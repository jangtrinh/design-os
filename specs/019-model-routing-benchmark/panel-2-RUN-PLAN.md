## Blinding protocol

1. Each arm × brief produces one build. 3 × 2 = **6 candidates**.
2. Candidates are labeled per brief in a shuffled order — **C1–C3** (Cadence), **H1–H3** (Haven).
3. The label→arm map is written to a **secret map file that the owner does not open** until every
   vote is cast. It is generated by shuffling, not chosen.
4. Candidates are rendered **live and full-fidelity** in a local viewer (same instrument class as
   panel 1 — real pages, not screenshots).
5. The owner records, **per brief**: a full ordinal ranking 1→3.
6. Only then is the map opened and the ranking de-anonymized.

**Leak discipline.** Nothing shown to the owner during voting may name a model, an arm, or a
pipeline stage. Build output is stripped of any generator metadata before it enters the viewer.

## Amendments

### A1 — generated imagery was suppressed in the first build set (2026-07-25)

**What happened.** The build prompts required offline `file://` safety and phrased it as
*"no remote images... Inline SVG / CSS / data URIs only."* That is stricter than offline safety
requires — a generated PNG written into the build directory is offline-safe — and it read to the
builders as a ban on raster assets. All six arms planned SVG/CSS only. This forced every arm onto
the last rung of the asset ladder in `knowledge/generation-craft-defaults.md:32-49`
(`project asset → approved source → generated asset → intentional no-image`), skipping the
documented *generated asset* rung: *"use the host's Codex image-generation capability backed by
GPT Image 2."*

**Whose fault.** Not a DESIGN:OS guidance gap. The guidance exists, is specific, and sits in the
exact file the pipeline builders were told to read first. The orchestrator's constraint overrode it.

**Why it matters.** All six arms were equally constrained, so build set 1 is internally fair — but
it measures **pipeline-minus-imagery vs bare**, not pipeline vs bare, and the handicap falls
hardest on the arms whose distinctive capability includes imagery planning. It also collides with
the owner's `e17` feedback (*"some of them still to simple"*): removing imagery pushes every
candidate toward exactly that failure mode. `benchmark-result.md` already records the pilot signal
as *"imagery-confounded"*; this reintroduced the confound from the opposite direction.

**Resolution (owner decision, 2026-07-25).** Rebuild all six arms with generated imagery permitted.
- Build set 1 is **retained** as `builds-noimage/` — a recorded imagery-suppressed control. It is
  not discarded, and the set-1 vs set-2 contrast is itself evidence about how much imagery carries.
- Build set 2 (`builds/`) permits the generated-asset rung for **all** arms, including A0, so the
  comparison stays fair. Assets are written locally; pages remain offline-safe.
- Codex image generation was verified working before the rebuild (1254×1254 8-bit RGB PNG, zero-key)
  rather than assumed from the capability note.
- **The panel ranks build set 2.** Set 1 was never shown to the owner, so no verdict is invalidated.

**Concurrency note.** With imagery enabled every builder may hold a Codex process, and A5 holds a
second for critique. Builders therefore run **two at a time** (2 builders + 2 Codex = 4) rather
than three, to stay inside the 4-agent ceiling.
