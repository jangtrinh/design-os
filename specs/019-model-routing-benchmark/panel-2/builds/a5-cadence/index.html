Most teams don't lack a deploy process. They lack one person who can explain it end to end — it lives half in a CI file, half in three Slack threads, and the rest in whoever shipped last.

deploy.yaml
stages:
  - build:
      run: make build
  - test:
      run: make test
  - gate:approval:
      require: 1 reviewer
  - deploy:
      run: cadence deploy prod

Define the pipeline once, in the repo it deploys.

A Cadence pipeline is a plain text file, reviewed in the same pull request as the code it ships. No separate UI to configure, no drift between what's documented and what actually runs.

  • Stages run in order, and stop on the first failure.
  • Each stage is a normal shell command — reuse your existing scripts.
  • The file is the documentation. Anyone can read what "deploy" means here.

Watch it happen, stage by stage — not after the fact.

Every stage reports status the moment it changes. No refreshing a CI tab, no digging through a log file to find where it actually stopped.

  • One list, one source of truth, shared by the whole team.
  • Failures point at the stage and the command that failed.
  • A stuck "awaiting review" is visible to everyone, not just the requester.

Deploy to prod is waiting on you.

A gate:approval stage pauses the pipeline until a named reviewer signs off. Nothing downstream runs until it's answered — the pipeline enforces the rule, it doesn't just document it.

Install it where you already work.

One binary, no daemon, no account required to try it locally.

brew install cadence && cadence init

Not on macOS? npm i -g cadence-cli works the same way.

  • Runs against any CI — it wraps commands, it doesn't replace them
  • cadence init scaffolds a deploy.yaml from your existing scripts
  • Uninstall any time: cadence uninstall, no residue
