## What

When design:os onboards a design system **from a codebase**, the deliverable is a **consumable
skill pack** — an Agent-Skills-compatible folder any fresh agent session can invoke to design
correctly with that brand. Generated by the split Claude Design proved: **the host model authors
the sources; the kernel deterministically emits everything machine-facing.** Three deliveries,
each one PR:

1. **The emitters.** `ui ds pack` — manifest, SKILL.md, adherence rules, card set, authoring
   scaffolds. Refuses an unsealed store; `ds status` learns a pack-freshness check.
2. **The instrument.** The code-onboard journey stops being advice and becomes a measured
   reading procedure with a coverage checklist and anti-invention guardrails.
3. **The consumption gate.** A fresh session, given only the pack, designs a screen that passes
   the pack's own adherence lint (Art III).

## Why

**Spec 009 ends the code road at "components register" — registry rows.** A row is not something
a user hands to an agent. `ui ds context` emits a context block *for the session that already has
the DS loaded*; nothing survives the session boundary in a form a stranger can invoke. The road
009 paves has no exit.

The PCP experiment is the missing last mile, and it is measured, not imagined: **36 registry
entries** (33 real components + 3 constant exports from `AppShell.jsx`), **33 `*.prompt.md`
usage laws**, **245 tokens**, **32 indexed cards** (27 `*.card.html` + 5 kit `index.html`),
**one `_adherence.oxlintrc.json` carrying 54 rules**. Every machine-facing file in it is a pure
function of the component contracts; every prose file is a judgement no compiler can make. That
is Art I's boundary, drawn by an independent implementation that never read our constitution.

**And it re-confirms four of our hard-won rules on someone else's codebase** — border-box 1px
(`readme.md:77`: a CSS `border` "steals a pixel from fixed-width children, which is exactly what
overflowed the tables by 1px"), count-before-target (0/32 screens used shadcn `Card`, so the
team-built `CardShell` is the real card), hole-is-a-decision (`readme.md:63`: an unshipped route
is "listed but not linked"), respect-their-DS (`readme.md:131` "Not built" — flagged, never
silently omitted). Four independent re-derivations is signal that the shape is invariant, not
PCP-specific.

## The architectural insight that changes the cost

Claude Design re-implemented 36 components as `.jsx` plus a **189KB `_ds_bundle.js`** because its
runtime is walled — it cannot execute the user's code. design:os lives **inside** the user's repo.
The components already exist, run, and are tested. **Therefore the pack points at their code
instead of copying it.** No React re-implementation, no bundle, no `ui_kits/` recreation. What
survives the deletion is exactly the part that carries knowledge: the bible, the per-component
usage law, the cards, and the machine-emitted rules.

## Pack anatomy

```
design/pack/                          # canonical, committed (see D1)
  SKILL.md                            # KERNEL — verbatim template, brand-substituted
  readme.md                           # MODEL — the design bible; required sections below
  tokens.css | tokens.pointer.md      # OWNER D4: copies ONLY when the source file carries a
                                      #   GENERATED header (R2's own heuristic); otherwise a
                                      #   pointer carrying repo-relative path + hash
  components/<Name>.prompt.md         # MODEL prose over a KERNEL frontmatter stub; each
                                      #   carries the repo path of the real implementation
  guidelines/*.card.html              # KERNEL — `ds preview --split` machinery, @dsCard tagged
  _adherence.rules.json               # KERNEL — derived from registry contracts + token set
  _adherence.oxlintrc.json            # KERNEL adapter (Should) — JSX/TSX repos only
  _pack_manifest.json                 # KERNEL — index + source hashes for drift detection
```

`readme.md`'s **required sections** (transcribed from direction, measured against PCP's 9 H2s):
`Sources` · `CONTENT FUNDAMENTALS` · `VISUAL FOUNDATIONS` · `ICONOGRAPHY` ·
`Intentional additions` · `Not built` · `Caveats`. Per Art II the requirement ships its linter in
the same commit: `ui ds pack --check` fails on a missing required section.

## Kernel surface (new): `ui ds pack`

Deterministic, no model calls, no network (Art I).

| Aspect | Contract |
|---|---|
| Inputs | sealed `design/` store (tokens + registry + manifest), `DESIGN.md`, the authored `readme.md` + `components/*.prompt.md` when they exist |
| Emits | `SKILL.md`, `_pack_manifest.json`, `_adherence.rules.json`, `guidelines/*.card.html`, authoring scaffolds for every unauthored source file |
| Refuses | an unsealed/tampered store (`DS_TAMPERED`, depends on 009 Phase 1); a registry with 0 components (`EMPTY_REGISTRY`) |
| Modes | `--check` (lint the pack, write nothing) · `--install <runtime>` (copy into the runtime's skills dir) · `--lint-adapter oxlint` (Should) |
| Freshness | `ds status` gains a `pack` block: pack hash vs registry `generation`; **stale is reported, never auto-repaired** |

`_pack_manifest.json` carries, per PCP's proven shape: `namespace`, `components[]`
(`name` + `sourcePath` — for us the **repo** path, not a copy), `cards[]` (`path`, `group`,
`name`, `subtitle`, `viewport`), `tokens[]` (`name`, `value`, `kind`, `definedIn`), `globalCssPaths[]`,
`brandFonts[]`, `source`. Added by us: `sourceHashes` (drift detection) and `gaps[]` (from
`ds specimen`).

## Journey surface (rewritten): the onboard instrument

The code branch of `templates/workflows/learn.md:85-136` moves into a new
`templates/workflows/code-onboard.md`, which `learn.md` Step 3 delegates to — the same
"follow the flow for the chosen source; **do not** restate its steps here" pattern the file
already uses (`learn.md:83`). All seven requirements are **measured in the PCP artifacts** and each
must be phrased as a check a reviewer can run.

| # | Requirement (Must unless noted) | Testable as |
|---|---|---|
| R1 | **Reading-order recipe** — `package.json` → app layout → token CSS → shell component → routes manifest → representative pages → fixture data; each entry point named with the knowledge dimension it answers; the first exploration issues them as ONE parallel batch | The workflow lists all 7 entry points in order with their dimension; the run's own summary names the file it read for each, or records "absent" |
| R2 | **Generated-file heuristic** — a `GENERATED — do not edit` header marks the highest-fidelity source: transcribe verbatim, never reinterpret, never round ("5px means 5px") | Any value sourced from a GENERATED file appears in the tokens byte-identical to the source; a rounded value is a gate failure |
| R3 | **Usage-count ranking** — count real usage per component across screens; the team-built tier outranks library presence | The summary carries a count per component; a library component with 0 usage sites is not ranked above a used team component (PCP: 0/32 screens used shadcn `Card`) |
| R4 | **Divergence → named props** — differences between consuming apps are intentional; model them as props, never normalize | Every divergence found between two consuming surfaces appears as a prop/variant axis in the registry record or in the "unverified" list — never silently merged |
| R5 | **Reason-with-value provenance** — carry the WHY next to every value | Each `readme.md` VISUAL FOUNDATIONS claim and each `prompt.md` "never" carries its reason inline (PCP: the 1px ring rule ships with the border-box reason) |
| R6 | **Coverage checklist** — the answer-ALL question lists for CONTENT / VISUAL / ICONOGRAPHY (gradients? hover? press? blur? emoji? casing per slot? unicode-as-icon? …). **"None" is an answer and is recorded** | Every checklist question has an answer in `readme.md`; an unanswered question is a gate failure, an explicit "none" is a pass (PCP: "Blur tokens exist and are unused") |
| R7 | **Anti-invention guardrails** — the source inventory IS the component list; enumerate-before-build and track against it; never end silently incomplete (emit "Not built"); no logo in source → no logo drawn; mid-run read failure → STOP and report read/unread; explicit anti-slop list | `readme.md` has a "Not built" section listing every source component without a pack counterpart; a pack claiming a component absent from the registry fails `ds pack --check` |

R1 supersedes `learn.md:188-198` §3a's "3–5 representative files" **for the pack road only** —
the recipe is a superset and PCP read the whole `src/` tree. §3a's audit rule survives verbatim:

**D3 — Adherence lint target: a linter-neutral rules file first, oxlint as an adapter.**
Measured what our engine already covers before choosing (direction's instruction).
`ds-usage-lint` is **HTML-input, colour-only by declared deferral** — three checks:
`undeclared-token`, `off-system-token`, `hardcoded-color` (`ds-usage-lint.ts:29-40`); it loads
`design.tokens.json` only and **never reads the registry**, so it knows nothing about component
contracts. PCP's config carries **54 rules**: 3 literal bans (hex, px, non-DS `font-family`),
**33 prop-allowlists**, **16 enum-allowlists**, 1 import-path restriction, 1 `forbid-elements`.
**Overlap = 1 rule of 54, and on a different input language** (our hex check matches CSS
properties in HTML; PCP's matches JS `Literal` nodes). Conclusion:

- **Must** — the kernel emits `_adherence.rules.json`, linter-neutral, in the findings-linter
  vocabulary Art II already fixes. Four rule kinds, exactly the kinds PCP needed:
  `token-ban` · `prop-allowlist` · `enum-allowlist` · `import-path`.
- **Must** — `ui ds-usage-lint --pack <dir>` consumes it, so design:os can enforce the subset that
  applies to HTML (our own generation output) with **no third-party dependency**. This is the
  linter half of Art II, in-house.
- **Should** — `ui ds pack --lint-adapter oxlint` emits `_adherence.oxlintrc.json` in PCP's proven
  selector shape, defaulted on when the registry's `sourcePath` extensions are `.jsx/.tsx`.
  Not Must: the gate repo may not be JSX, and an emitter with no consumer is speculative (Art IX).
- **Could** — an ESLint flat-config adapter, if a gate repo demands it.

**D4 — `templates/*.dc.html` starting points: OUT of v1**, as direction recommends. Evidence

## Acceptance criteria

1. **The pack is a function of the store.** `ui ds pack` on a sealed DS emits `SKILL.md`,
   `_pack_manifest.json`, `_adherence.rules.json`, and the card set with **byte-identical output
   for identical input** (Art I). Re-running changes nothing on disk.
2. **The pack refuses to lie about its source.** `ds pack` on an unsealed/tampered store exits
   non-zero with `DS_TAMPERED` and writes nothing. On a 0-component registry: `EMPTY_REGISTRY`.
   Never a pack that looks complete over a store that is not.
3. **The boundary holds.** No kernel-emitted file contains prose the model authored, and no
   model-authored file is overwritten by a re-run of `ds pack` (the scaffold is written **only**
   when the target does not exist).
4. **Required sections ship with their linter.** `ui ds pack --check` fails when `readme.md` is
   missing any of the seven required sections, or when `readme.md` claims a component the
   registry does not carry (Art II, Art VIII).
5. **The adherence rules are derived, not written.** Every rule in `_adherence.rules.json` traces
   to a registry record or a token path; a rule with no source is a build failure. `ui ds-usage-lint
   --pack` consumes the file and reports in the standard findings shape
   (`{checkId, severity, message, line?}` → `{findings, errorCount, warningCount}`, exit 1 on errors).
6. **Freshness is visible, never auto-healed.** After a `registry register`, `ds status` reports
   the pack as stale with the generation it was built from. It does not rebuild.
7. **The instrument is auditable.** A code-onboard run produces a summary naming, per R1 entry
   point, the file read or "absent"; per R3, a usage count per component; per R6, an answer to
   every checklist question including explicit "none"; per R7, a "Not built" list.
8. **Art III — the two-session consumption test.** The gate runs on **dana-desktop** (owner D3;
   it is also 009's own gate repo, so the road and its exit are proven on one tree). Then: a
   **fresh Claude Code session on this machine**, given **only** the pack, produces one screen
   that (a) passes the pack-emitted adherence lint, (b) passes `ui ds-usage-lint --pack`, and
   (c) passes a reviewer's DS-fidelity check against `readme.md`. A different runtime
   (Antigravity) is **deferred**, and the deferral is stated in the gate write-up — not silently
   dropped. The screen is **evidence, filed under `specs/025-onboard-pack/reports/`**; it does not
   ship into the pack (owner D6). **A repo where the pack fails is a finding, reported** — not a
   quiet omission.
9. Every phase = 1 PR, three-tier pipeline (Art V), human merge; four gates + `ui knowledge check`
   + `npm test` green. New modules < 200 lines (Art IX).

## Non-goals

- **Claude-Design-compatible output** (`.jsx` quad, `_ds_bundle.js`) — future phase, explicit door.
- **Re-implementing user components in any form.** The pack points; it never copies code.
- **Slides / UI-kit recreation.** PCP needed `ui_kits/` as proof inside a walled runtime; our proof
  is the consumption gate against the real repo.
- **Healing a tampered store** — that is 009 Phase 1's owner-call.
- **Parameterized starting points** (`*.dc.html`) — D4, owner-confirmed.
- **Shipping the gate's output screen inside the pack** (owner D6). It is evidence in
  `specs/025-onboard-pack/reports/`. A pack that carries its own test output starts teaching the
  test instead of the system.
- **A Figma-side pack.** This spec is the code road's exit only; the Figma road already ends in
  `ingest-figma-ds` + `CONVENTIONS.md`.
