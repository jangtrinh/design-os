Quy Trình 5 Bước & Các STOP-Gates Bắt Buộc

Tuân thủ thứ tự thiết lập để không bao giờ gặp lỗi lệch mã băm hoặc sai danh tính Agent.

5 Bước Khởi Tạo Chuẩn Xác
  1. Bước 0: Chạy ui onboard xem checklist và ui scan.
  2. Bước 1: Chọn cổng (E1–E6) để seal kho design/.
  3. Bước 2: Chạy cả 2 lệnh Doctor: ui doctor và design-os doctor --versions.
  4. Bước 3: Điền Never/Always/Voice vào design/soul.md rồi chạy ui ds soul check.
  5. Bước 4: Khởi tạo đội ngũ Agent: ui agents init.
⚠️ STOP-GATE 1: NAMING HYGIENE
Luôn truyền --name khi import token

Nếu bỏ qua --name <slug>, hệ thống mặc định đặt tên là imported-ds và sau này toàn bộ AI Agent sẽ bị đặt tên là designer-imported-ds.

🛑 STOP-GATE 2: GIT PREREQUISITE
Bắt buộc phải là Git Repository

Dự án phải có .git (chạy git init). Nếu không có git, các lỗi lệch hash registry sau này sẽ không thể diff và truy vết.

6 Động Từ Thường Nhật (Daily Verbs)

Tương tác bằng ngôn ngữ tự nhiên trong CLI. AI tự chuyển hóa thành kế hoạch và code chuẩn mực.

> /ui:generate landing page for an AI developer tool, brutalist-editorial, dark theme

Biến yêu cầu sơ khai thành brief chuẩn, dựng layout gắn token, kiểm tra qua 6 linter.

Quy Trình Xử Lý Lỗi

Quy Trình Triage Lỗi & 2 Nguyên Tắc Vàng

Đọc kết quả linter một cách khoa học để đưa ra quyết định Iterate hay Escalate.

Quy Trình Triage 3 Bước
  • 1. Luôn đọc cờ --json: Exit code 1 có thể do gọi sai flag (BAD_ARG) hoặc lỗi thiết kế thực sự. Xem envelope trước khi sửa code.
  • 2. Exit 0: Không có lỗi severity error → Sẵn sàng phát hành (Ship).
  • 3. Exit 1: Có lỗi nghiêm trọng → Chọn Iterate (sửa code và quét lại) hoặc Escalate (báo cáo mâu thuẫn yêu cầu).
NGUYÊN TẮC VÀNG 1
Xác Minh Trước Khi Sửa (Verify Before Fix)

Kiểm tra xem cặp màu hoặc class bị linter bắt lỗi có thực sự được render trên màn hình không trước khi vội vàng sửa đổi file token gốc.

NGUYÊN TẮC VÀNG 2
A11y Luôn Thắng Phong Cách (A11y Always Wins)

Nếu màu sắc từ yêu cầu của người dùng vi phạm độ tương phản WCAG AA, bắt buộc phải ưu tiên sửa màu A11y và báo cáo minh bạch cho người dùng.

13 • 14 Hard Linter Rules
Sàn Chất Lượng Tất Định

14 Luật Kiểm Định Máy Cứng (Machine Floor)

Các linter taste-lint, validate-layout, content-lint tự động phát hiện và chặn đứng các lỗi AI code rác.

CHUYỂN ĐỘNG & LAYOUT SAFETY
  • no-transition-all: Cấm dùng transition: all gây drop FPS.
  • no-layout-keyframes: Cấm animate top, left, width, height.
  • require-reduced-motion: Bắt buộc có media query giảm chuyển động.
  • no-100vw-scroll: Cấm w-[100vw] gây thanh cuộn ngang khó chịu.
  • no-root-overflow-hidden: Cấm overflow-x: hidden ở thẻ html/body làm liệt sticky.
TYPOGRAPHY & NỘI DUNG UX
  • min-body-font: Cấm font chữ body nhỏ hơn 16px.
  • no-font-scale-sprawl: Cảnh báo > 7 cỡ font tự chế, chặn khi > 10 cỡ.
  • no-italic-headings: Cấm tiêu đề display dùng font chữ nghiêng.
  • no-pure-black-shadow: Cấm bóng đổ đen tuyệt đối rgba(0,0,0,...).
  • no-placeholder-copy: Cấm văn bản rác vô nghĩa, tên giả vô định, link rỗng.

Delivery Checklist & Phân Loại Semver PR

Tạo tài liệu component tự động, trang specimen độc lập và tự động tính toán mức độ breaking change cho Pull Request.

5 LỆNH TRONG DELIVERY CHECKLIST
# 1. Kiểm tra thiếu trạng thái component
ui ds specimen --dir . --strict --json

# 2. Tái tạo tài liệu component từ Registry
ui ds docs --dir . --out docs/components.md

# 3. Tạo trang specimen HTML độc lập
ui ds preview --dir . --out preview.html

# 4. Quét Visual Regression component kit
design-os vr-matrix --project .

# 5. Xuất Changelog lịch sử thay đổi
ui changelog --dir . --format markdown
PHÂN LOẠI SEMVER (ui ds diff)
ui ds diff base head --format pr-comment
  • MAJOR (Breaking): Xóa token/component đang dùng; hoặc thay đổi màu sắc vượt ngưỡng Delta EOK.
  • MINOR (Additive): Thêm mới token/component hoặc thêm variant mà không ảnh hưởng code cũ.
  • PATCH: Sửa lỗi chính tả token, vi chỉnh không gây lệch thị giác.
